### 0.2 문서에 없던 핵심 발견

1. **700,000자 초과의 주원인은 모델 출력이 아니라 `rowSources`다.** `Analysis.rowSources`는 입력 행마다 `{fileId, sheet, row}`를 담고(`workbook.ts` 308행), `tool.ts` 514행의 700,000자 검사에 포함된다. 합성 측정에서 10,869행의 `rowSources`만 **684,278자**, 전체 표를 넣은 `analysis`는 **1,311,006자**였다. 입력이 약 10,000행이면 결과 표를 한 행으로 줄여도 `rowSources`(약 63만 자)와 `sourceRows`만으로 한도에 근접한다. 1,000·2,000점 샘플링은 나머지 행이 `excluded`에 들어가야 하므로(약 30만 자 추가) 오히려 크기를 줄이지 못한다. 실제 대화의 “700KB 초과 → 샘플링 제안 → 500개 제한” 흐름은 구조적으로 예정된 실패였다. 오류 문구 “표를 700KB 이내로 집계”는 모델이 통제할 수 없는 부분까지 표 탓으로 돌린다.
2. **완료 경로도 1MB checkpoint 한도에 걸린다.** `finish()`는 `excelState.latest.analysis` 전체를 checkpoint에 넣고(`tool.ts` 161~163행), BusinessFlow는 완료 시에도 1,000,000자를 검사한다(`flow.ts` 165행). 렌더링 한도를 모두 풀어도 10,869행 결과는 파일 생성 후 이 검사에서 실패한다. F의 checkpoint 저장 방식 변경은 선택이 아니라 필수다.
3. **이전 완료 작업의 답변이 다음 작업으로 그대로 넘어간다.** `BusinessFlow.start()`는 같은 thread의 마지막 완료 run에서 `excelState`와 `clarifications`를 복사하고(`flow.ts` 48~52행), `request`도 이전 값을 유지하므로 `tool.ts` 300~305행에서 기존 상태가 재사용된다. 저장된 `item.answer`가 항상 우선하므로 “10,000행까지만 그래프” 같은 과거 답변은 후속 요청에서도 수정할 수 없다. A의 범위에 포함해야 한다.
4. **답변이 3개를 넘으면 매 질문마다 모델 호출이 1회 추가된다.** `answers.length >= 3`이면 `recheck`가 켜져 질문 전에 한 턴을 더 소비한다(`tool.ts` 468~472행). 네 번째 이후 질문 구간의 지연 요인이다.
5. **출력 잘림을 감지하지 않는다.** `complete()`는 `finishReason`을 계산하지만(`modelClient.ts` 283행) 반환하지 않는다. 10,000 tokens에서 잘린 `execute` JSON은 JSON 파싱 오류로만 보이고 수정 루프를 1회 소비한다.
6. **TGA 10,869행은 입력 단계에서 먼저 막힌다.** 범위당 10,000행(`workbook.ts` 217행)과 전체 합계 10,000행(301행)을 모두 넘는다. §7의 변경 단위 3에 `excel/workbook.ts`가 빠져 있었다(본문 보완).
7. **`tool.version`을 올려도 이전 데이터 읽기는 피할 수 없다.** 대기 중 run은 거부되지만(`flow.ts` 92행), `start()`의 이전 완료 run checkpoint 복사는 버전을 확인하지 않는다. 새 코드는 구 `answer1~3`·clarification 형식을 반드시 읽어야 한다. 또 92행 예외는 `try` 밖에서 발생해 입력 카드 대신 submit 실패로 끝난다.

## 1. 결론과 우선순위

이번 지연은 파일을 읽거나 행 수를 세는 작업보다 **LLM이 계획·계산 코드를 생성하고, 실행 제한이나 결과 형식 오류를 만난 뒤 다시 생성하는 반복**에서 주로 발생한 것으로 판단된다. 추가 의견이 제대로 반영되지 않는 현상에는 실제 답변 상태 관리 결함도 있다.

사용자의 입력은 자유 텍스트다. 내부적으로 JSON에 담아 모델에 전달하는 방식 자체는 문제가 아니다. 현재 조건과 과거 답변이 충돌하고, 실행 가능성을 늦게 검사하며, 내부 오류를 사용자 확인 질문으로 돌려보내는 흐름을 고쳐야 한다.

| 순서 | 작업 | 기대 효과 | 완료 기준 |
| --- | --- | --- | --- |
| 1 / P0 | 최신 답변 반영, 질문 ID 충돌, `chart` 계약 불일치 수정 | 잘못된 재질문과 불필요한 실패 제거 | 답변 수정·네 번째 이후 질문·구버전 대기 상태·차트 결과 회귀 테스트 통과 |
| 2 / P1 | 실행 전 제약 검사, 오류 분류, 최소 시간 계측 | 불가능한 선택지와 무의미한 모델 재시도 방지 | 알려진 제약은 코드 생성 전에 설명하고 단계별 시간이 남음 |
| 3 / P1 | 구조화된 기본 차트 실행 경로, 이중축, 전체 데이터 처리 | TGA 예제를 실제로 완료 | 선택 시트 전체 10,869개 행, 숫자형 X축, Y축 두 개로 HTML 생성 |
| 4 / P2 | 재개 시 파일 프로파일 재사용, 모델 컨텍스트 축소 | 반복 작업의 추가 비용 감소 | 변경 없는 파일의 불필요한 재분석 감소, 출처·변경 검사 유지 |

전체 Harness를 다시 설계할 필요는 현재 근거에서 확인되지 않았다. 개선의 주된 위치는 `BusinessFlow`와 `electron/excel/`이다. Harness는 요청의 시작·재개·취소·workflow 변경을 계속 담당한다.

## 2. 대표 작업과 파일 확인 결과

### 2.1 사용자 요청

> B행에 있는 것들을 X축, C행에 있는 것들을 Y1축, D행에 있는 것들을 Y2축으로 해서 그래프를 그려 HTML로 만들어줘. X축은 Temperature(℃), Y1축은 Weight Loss(℃), Y2축은 Deriv. Weight(%/℃).

파일 문맥에서 B·C·D는 **열**로 해석할 수 있다. 기존 대화에서 선택한 시트는 `1006R1-V normal`이다. 같은 작업을 재개할 때 이 선택을 다시 물을 필요는 없다.

별도 Python 표준 라이브러리 ZIP/XML 읽기 검사에서 전체 시트의 구조와 B·C·D 숫자 데이터를 훑는 데 약 **1.34초**가 걸렸다. 이는 진단용 단일 측정이며 앱의 ExcelJS 파싱 성능이나 차트 렌더링 시간을 측정한 값은 아니다.

일부 다른 시트는 마지막 사용 행과 B·C·D 숫자가 모두 존재하는 행 수가 다르다. 파일 크기나 `rowCount`만으로 유효 데이터 개수를 판단하면 안 된다. 결측·구간 경계도 확인해야 한다.

### 2.2 실제로 필요한 사용자 확인

요청의 `Weight Loss(℃)`와 원본의 `Weight(%)`는 의미와 단위가 다르다. 다음을 구분해야 한다.

- C열을 그대로 표시: `Weight (%)`.
- 감소량으로 변환: `Weight Loss (%)`. 기준이 `100 - Weight`인지, 최초 측정값 대비 감소량인지 확인 필요.

단위를 임의로 바꾸거나 감소량을 자동 계산하지 않는다. 이 확인은 결과의 의미를 바꾸므로 타당한 Human-in-the-loop 질문이다. 반면 파일에서 읽을 수 있는 행 수나 프로그램의 제한 때문에 같은 작업을 여러 차례 되묻는 것은 줄여야 한다.

**측정의 한계:** 현재 trace에는 구체적인 phase, 모델 호출별 duration, 실패한 계획 원문이 없다. 위 역할 구분은 이벤트 순서와 소스에 근거한 추정이며 서버 처리·네트워크 시간을 분리한 측정은 아니다. 세 번의 내부 오류가 모두 같은 `chart` 오류였다고도 단정할 수 없다. 최종 `chart` 오류와 전체 경과 시간은 메시지에서 확인된다. 모델이 이후 설명한 “700KB 초과”도 내부 결과 원문으로 독립 검증된 것은 아니다.

## 4. 현재 처리 구조

```text
사용자 텍스트 / 입력 카드
  → Harness가 기존 excel_work 작업으로 재개
  → BusinessFlow: 입력 저장, 파일 재읽기·fingerprint 확인
  → Excel tool: 파일 프로파일, 저장된 관찰·답변 준비
  → LLM: inspect / execute / inspect_result / finish / ask 중 선택
      ├─ inspect: 파일 열람 후 다시 LLM
      ├─ execute: 생성 코드 실행·결과 검증
      │    ├─ 실패: 오류를 넣고 다시 LLM
      │    └─ 성공: 즉시 출력 또는 다시 LLM으로 검토
      └─ ask: checkpoint 저장 후 사용자 입력 대기
```

명시적으로 엑셀 작업을 선택한 요청은 초기 모델 라우팅을 생략한다. 확인 답변은 기존 BusinessFlow로 돌아간다. 각 엑셀 단계가 ChatWorkflow의 일반 대화/RAG 정책 루프를 거치는 구조는 아니다.

한 제출 안에서는 worker와 파싱 캐시를 재사용한다. 사용자 답변으로 재개하면 새로운 제출·worker 세션을 시작한다. 저장된 관찰·계산 일부는 복구하지만 일반 분석 경로는 전체 프로파일을 다시 만든다. 저장된 보고서의 재출력은 별도 경로가 있다.

## 5. 확인된 문제와 개선 방향

### A. 최신 답변과 과거 답변이 동시에 전달됨 — P0

현재 답변 병합은 다음과 같다.

```ts
answer: item.answer ?? values[item.key] ?? ""
```

저장된 `item.answer`가 있으면 현재 입력의 수정값보다 우선한다. 동시에 `answers`에는 현재 입력이 담기므로 같은 질문에 상충하는 내용이 모델에 전달될 수 있다.

실제 DB에서 `answer2`의 현재 입력은 “데이터 간격 조정”이었지만 저장된 clarification에는 “10,000행까지만 그래프”가 남아 있었다. 네 번째 질문부터는 `answer3`를 재사용하며, 실제로 서로 다른 질문 두 개가 같은 키를 사용했다. 이는 최신 지시 해석을 방해하는 확인된 결함이다. 다만 개별 모델 판단의 원인을 전부 이 결함으로 확정할 수는 없다.

**개선:** 현재 유효한 답변을 한 곳에서 관리하고, 과거 답변은 변경 이력으로 구분한다. 질문별 고유 ID와 현재 대기 질문을 연결한다. 선택형 질문은 표시 문구 대신 안정적인 선택지 ID로 받되 자유 텍스트 수정도 허용한다. 채팅으로 여러 조건을 수정하면 현재 질문의 답변인지 다른 조건의 변경인지 해석해 해당 조건만 갱신한다.

`??`의 순서만 바꾸면 재사용 중인 `answer3`의 새 답변이 과거 질문까지 덮을 수 있다. 키 충돌 수정과 함께 처리해야 한다. 질문마다 필드를 무한 추가하면 BusinessFlow의 30개 필드 제한에 걸리므로 현재 입력 카드에는 필요한 항목만 유지하고 이력은 checkpoint에 둔다.

근거: [tool.ts](../electron/excel/tool.ts) 56, 261, 477행 / [flow.ts](../electron/business/flow.ts) 63, 300행.

> **타당성 검토 (A)** — 판정: 타당 / 규모 M / 위험 중
>
> - 확인: `tool.ts` 268행 `item.answer ?? values[item.key]`, 477행 `answer${Math.min(answers.length + 1, 3)}`, 59행 `regex(/^answer[1-3]$/)` 모두 문서와 같다. 30개 필드 제한(`flow.ts` 302행)도 맞다. 현재 키가 3개로 묶여 있어 필드 수는 최대 8개라 당장 한도 문제는 없고, 설계 시 주의사항으로 보면 된다.
> - 보완 1: `flow.ts` 48~52행이 이전 완료 run의 `clarifications`를 새 run으로 복사한다(§0.2-3). 범위에 포함해야 한다.
> - 보완 2: 입력 카드에서 기존 답변만 고친 경우 `flow.ts` 97행 `revised` 판정에 `answerN`이 없어 수정으로 인식되지 않는다. 최신 답변 판정을 tool에만 두지 말고 BusinessFlow가 “이번 제출에서 바뀐 키”를 넘기도록 하는 편이 단순하다.
> - 구현 방법: clarification 항목에 `id`(예: `q<n>`)와 `answers: {value, at}[]` 이력을 두고, 입력 카드 필드 키는 `answer`(현재 대기 질문 하나)만 쓰는 방식이 30개 제한과 키 충돌을 함께 해결한다. 구 형식은 `answer1~3`를 순서대로 매핑하는 읽기 함수 하나로 흡수할 수 있다.
> - 위험: 구 checkpoint 호환(§0.2-7). 대기 중 run과 이전 완료 run 복사 두 경로를 모두 테스트해야 한다.

### B. `chart` / `charts` 안내와 검증 계약 불일치 — P0

프롬프트는 `chart` 또는 `charts` 중 하나를 사용하라고 하지만 `analysisResult`는 `chart: chartSpec.nullable()`을 필수로 요구한다. `charts`만 반환하면 `chart`가 없다는 오류가 발생한다.

실제 스키마에 최소 결과를 넣어 검증했을 때 `chart` 생략은 사용자와 동일한 오류를 만들었고, `chart: null` 추가는 통과했다. 사용자의 확인 답변을 JSON으로 잘못 입력해서 발생한 오류가 아니다.

**개선:** 기존 결과를 읽는 호환성을 유지하면서 생략된 `chart`를 안전하게 정규화하고, 프롬프트·결과 스키마·sandbox 오류 안내를 일치시킨다. 차트가 두 경로에 동시에 존재하는 경우, 잘못된 열 참조, 비유한 숫자 등의 검증은 유지한다. 장기적으로 단일 `charts` 표현을 사용할지는 별도 결정한다.

근거: [contracts.ts](../electron/excel/contracts.ts) 58~74, 107행 / [tool.ts](../electron/excel/tool.ts) 146~147행 / [sandbox.ts](../electron/excel/sandbox.ts).

> **타당성 검토 (B)** — 판정: 타당 / 규모 S / 위험 낮음
>
> - 확인: `contracts.ts` 68행 `chart: chartSpec.nullable()`(필수), 69행 `charts` optional, 107행 동시 사용 거부. 프롬프트는 “chart 하나 또는 charts 배열 중 하나”라고 안내한다. 문서 설명 그대로다.
> - 구현: 68행을 `.nullable().optional()`로 바꾸면 끝난다. `reportCharts`(74행)와 `validateResult`(107~108행)는 이미 `chart`가 없을 때를 처리한다. 저장된 결과는 다시 parse하지 않으므로 기존 checkpoint 영향이 없다.
> - 같이 고칠 곳: sandbox 오류 문구(`sandbox.ts` 15행)가 `return {tables, excluded, notes, chart}`를 요구해 모델을 `chart` 쪽으로 유도한다. 기존 테스트 fixture는 모두 `chart: null`이므로 생략 케이스 테스트를 1개 추가한다.

### C. 알려진 제약을 실행 후 발견하며 불가능한 선택지까지 제안 — P1

현재 제한은 Excel 자체의 한계가 아니라 앱의 입력·결과·렌더링 정책이다.

| 대상 | 현재 제한 / 검사 |
| --- | --- |
| 파일 | 파일당 5MiB 이하, 선택 파일 1~10개 |
| 입력 범위 | 범위당 연속 최대 10,000행; 읽은 전체 입력 행 합계도 최대 10,000개 |
| 입력 직렬화 | `JSON.stringify(rows).length`가 `8 * 1024 * 1024` 이하 |
| 결과 표 | 최대 20개, 합계 5,000행, 표당 20열 |
| 차트 | 최대 10개, 각 차트가 참조하는 표는 1~500행 |
| sandbox 반환 | JSON 문자열 길이 `4 * 1024 * 1024` 이하 |
| 분석 checkpoint 대상 | `JSON.stringify(analysis).length`가 700,000 이하 |
| 업무 checkpoint | JSON 문자열 길이 1,000,000 이하 |
| (검토 추가) 실행 시간 | QuickJS 코드 실행 5초, worker 작업당 30초, 제출당 15분 |
| (검토 추가) 코드·응답 | 생성 코드 30,000자, 모델 응답 60,000자, 출력 10,000 tokens |
| (검토 추가) 출력 파일 | 파일당 20MB, 합계 60MB, 최대 3개 |

문자열 `.length`는 UTF-8 파일 바이트 수가 아니다. “700KB” 등의 현재 오류 표현과 실제 검사 단위도 구분해야 한다.

파일 프로파일에 행 수가 이미 있어도 LLM이 전체 계획과 코드를 생성한 뒤 입력 제한에 걸릴 수 있다. 데이터는 생성 코드보다 먼저 읽으므로, 코드 안에서 샘플링하는 것만으로 입력 10,000행 제한을 우회할 수 없다. 출력 크기는 생성 후에야 정확히 알 수 있지만, 고정 행 수·열 수·지원 차트 같은 제약은 사전 검사할 수 있다.

**개선:** 파일 메타데이터 검사 → 짧은 실행 계획 → 제약 검사 → 필요한 확인 → 실행 순서로 처리한다. 동일한 제약 정의를 모델 안내와 실행 검증에서 사용한다. 예상 가능한 제한 오류는 전체 코드 재생성 대신 실행 가능한 대안으로 처리한다. 출력·메모리 제한은 실행 후 검사도 유지한다.

근거: [workbook.ts](../electron/excel/workbook.ts) 25, 211, 280행 / [contracts.ts](../electron/excel/contracts.ts) 60, 81행 / [tool.ts](../electron/excel/tool.ts) 514행 / [flow.ts](../electron/business/flow.ts).

> **타당성 검토 (C)** — 판정: 타당, 일부 수정 / 규모 M / 위험 낮음~중
>
> - 행 번호 정정: 범위당 10,000행은 `workbook.ts` 217행, 합계 10,000행은 301행, 8MiB 검사는 271·307행이다(25행은 5MB 파일 검사로 맞음).
> - 가정 수정: “출력 크기는 생성 후에야 정확히 알 수 있다”는 700,000자 검사에는 절반만 맞다. 크기의 큰 몫인 `rowSources`는 입력 행 수와 시트명 길이로 실행 전에 계산된다(§0.2-1). 사전 검사에 넣을 수 있다.
> - 확인: 데이터 추출(`readAnalysisInputs`)이 `runAnalysis`보다 먼저 실행되므로 코드 내 샘플링으로 입력 한도를 피할 수 없다는 설명은 맞다(`excel.worker.ts` 14~15행).
> - 구현: 제한 상수가 6개 파일에 흩어져 있다. `excel/limits.ts`로 모으고 프롬프트 문자열도 그 값으로 생성하면 안내·검증 불일치가 재발하지 않는다. worker와 main 모두 TS를 import하므로 기술적 장애는 없다. 사전 검사는 `tool.ts` 513행 `io.analyze` 직전에 profile의 `rows`를 써서 worker 호출 없이 할 수 있다.
> - 한계: 사전 검사도 모델이 계획을 한 번 만든 뒤 동작한다. 첫 호출부터 불가능한 계획을 피하려면 profile·프롬프트에 “이 시트는 한 번에 처리 가능한 행 수를 넘음” 같은 사실을 함께 넣어야 한다.

### D. 짧은 확인·수정도 전체 모델 생성 루프로 돌아감 — P1

모델은 매 턴 요청·답변·파일 프로파일·관찰·계산 요약·이전 응답·실패 사유를 받는다. `execute`에는 JavaScript 코드가 포함된다. 최대 출력은 10,000 tokens이며, 모델 클라이언트는 스트림을 내부에서 모두 모은 뒤 문자열을 반환한다. UI는 그동안 동일한 진행 문구를 표시한다.

제출당 최대 24턴, 파일 열람 12회, 계산 시도 4회, 연속 오류 수정 2회다. 최초 실패 후 수정 2회까지 실패하면 최종 오류가 나온다. 성공한 중간 작업은 오류 카운트를 초기화할 수 있다. 한도가 있다는 사실만으로 짧은 작업의 지연을 막지는 못한다.

**개선:** 열 선택과 차트 작성처럼 정형화할 수 있는 요청에는 작은 계획을 검증된 코드로 실행하는 경로를 추가한다. 기존 범용 코드 실행 경로는 복잡한 계산에 유지한다. 선택지 클릭은 해당 조건을 직접 갱신하고, 자유 텍스트 변경은 필요한 조건만 해석한다. 이미 검증한 결정적 계산에 불필요한 모델 검토를 붙이지 않는다.

JSON이나 검증 자체를 없애는 것이 아니라 **모델이 생성해야 하는 내용과 호출 횟수를 줄이는 변경**이다.

근거: [tool.ts](../electron/excel/tool.ts) 47, 326, 548행 / [runtime.ts](../electron/agent/runtime.ts) 208행 / [modelClient.ts](../electron/agent/modelClient.ts) 271행.

> **타당성 검토 (D)** — 판정: 방향 타당, 단계 분리 권장 / 규모 빠른 개선 S + 정형 경로 M~L / 위험 중
>
> - 확인: `LIMITS`(47~54행), 10,000 tokens(`runtime.ts` 209행), 스트림 수집 후 반환(`modelClient.ts` 276~282행), 고정 진행 문구(328~332행) 모두 맞다. inspect·inspect_result·execute 성공 시 `repairs = 0`이 되어 한 제출에서 최대 24회 모델 호출이 가능하다는 해석도 맞다.
> - 빠른 개선(S, 계약 변경 없음): ① `finishReason === "length"`를 감지해 “응답이 잘림, 코드를 줄여라”로 구분(§0.2-5) ② `answers.length >= 3`만으로 recheck를 켜지 않기(§0.2-4) ③ 오류마다 전체 profile을 다시 보내는 대신 실패 시 `failure`와 직전 계획만 보내는 축소 프롬프트.
> - 정형 경로 구현 제안: 새 실행기를 만들기보다 `planResponse`에 `kind: "chart"`를 추가하고, tool이 그 계획에서 **고정 템플릿 코드**를 만들어 기존 `io.analyze`(QuickJS + `validateResult`)로 실행하는 방식을 권한다. 신뢰 경계·검증·출처 규칙을 그대로 재사용해 새 공격면이 거의 없다. 모델은 열 번호·축·라벨만 내므로 출력이 수십 tokens 수준으로 준다.
> - 위험: 계획 해석(어떤 요청을 `chart`로 볼지)을 모델에 맡기는 한 호출 1회는 남는다. “선택지 클릭은 모델 호출 없이 적용”은 선택지가 계획 필드와 1:1로 묶일 때만 가능하므로 A의 질문 ID 설계와 같이 해야 한다.

### E. 요청한 이중축과 숫자형 선 그래프를 현재 계약이 표현하지 못함 — P1

`chartSpec`은 단일 `x`, `y`만 가지며 보조 Y축과 여러 시리즈의 축 배정이 없다. HTML 렌더러도 하나의 Y값 배열을 그린다. `charts`를 두 개 만드는 것은 같은 그래프에 왼쪽·오른쪽 Y축을 두는 것과 다르다.

현재 `line`은 X좌표를 데이터 인덱스로 계산하고, `scatter`만 실제 숫자 X값을 사용한다. 온도 간격이 일정하지 않은 TGA에 인덱스 간격을 사용하면 그래프 해석이 달라질 수 있다. 그런데 실제 대화에서는 이중축을 유지하겠다고 안내했다.

**개선:** 숫자형 X축, 복수 시리즈, 시리즈별 Y축·단위·범례를 명시적으로 지원한다. 원본 측정 순서를 기본으로 보존한다. 온도 값의 작은 역행이나 반복값을 임의 정렬·병합하지 않는다. 형식별 지원 여부를 먼저 검사하고, 미지원 기능을 모델이 제공한다고 약속하지 않게 한다.

근거: [contracts.ts](../electron/excel/contracts.ts) 58행 / [render.ts](../electron/excel/render.ts) 36, 55행 / [xlsxCharts.ts](../electron/excel/xlsxCharts.ts).

> **타당성 검토 (E)** — 판정: 타당 / 규모 HTML·PDF M, XLSX M(별도) / 위험 중
>
> - 확인: `chartSpec`은 단일 `x`·`y`(58행), `chartSvg`는 `line`일 때 X를 인덱스로 둔다(`render.ts` 55행 `chart.type === "scatter" ? Number(...) : i`). XLSX도 `line`을 `catAx`(범주축)로 만든다. 문서 설명이 맞다.
> - PDF: `finish()`가 `renderHtml(report, false)`를 인쇄해 PDF를 만든다(`tool.ts` 169행). SVG 이중축을 구현하면 PDF는 거의 추가 비용 없이 따라온다. “HTML 우선, PDF는 별도 판단”보다 “HTML·PDF 동시, XLSX 별도”가 실제 비용 구조에 맞다.
> - XLSX: OOXML 이중축은 `scatterChart` 두 개와 축 쌍 두 개(`c:crosses val="max"`)가 필요하다. 현재 문자열 템플릿 방식으로 가능하지만 Excel·LibreOffice·Numbers 렌더링 확인이 필요해 별도 단계로 두는 것이 맞다.
> - 하위 호환: `chartSpec`에 `series?: {y, axis}[]`, `xScale?: "linear" | "category"`를 선택 필드로 추가하면 기존 `x`/`y` 결과를 그대로 읽는다. 1만 점 SVG는 원 1만 개 + polyline으로 약 66만 자다. 선 차트는 점 마커를 빼면 절반 이하로 줄고, `Math.min(...values)` 같은 spread는 큰 배열에서 루프로 바꾸는 것이 안전하다.

### F. 차트 데이터와 보고서 표·출처·checkpoint 용량이 결합됨 — P1

차트가 결과 표를 참조하므로 전체 데이터를 그리려면 표의 행 제한과 결과 저장 제한까지 통과해야 한다. 차트만 필요한 작업에도 행별 결과·출처 구조의 크기가 영향을 준다. 제한 숫자를 하나 올리는 것만으로는 다른 제한에서 다시 실패한다.

**개선:** 차트가 사용하는 숫자 데이터와 사람이 읽는 보고서 표의 행 정책을 분리한다. 원본 데이터는 로컬 worker에서 처리하고 모델에는 열·단위·개수·요약만 전달한다. 출처 연결은 유지하되 불필요한 반복 메타데이터를 줄인다. checkpoint에는 작업 조건과 재현 가능한 참조를 저장하고 대량 데이터 저장 방식은 실제 크기를 측정해 결정한다.

첫 목표는 선택 시트의 10,869개 전체 점을 처리하는 것이다. 먼저 전체 데이터 렌더링 성능을 측정한다. 필요할 때만 표시용 축약을 검토하며, 원본 계산 데이터는 보존한다. 첫 10,000행 절단이나 단순 N행 간격 샘플링을 자동 기본값으로 두지 않는다. TGA 미분 피크·끝 구간이 사라질 수 있기 때문이다. 사용자가 명시적으로 요청한 범위 축소는 그 조건대로 처리한다.

> **타당성 검토 (F)** — 판정: 타당, TGA 완료의 선행 조건 / 규모 L / 위험 중~높음
>
> - 10,869행을 통과하려면 다음 한도를 **모두** 바꿔야 한다: 입력 범위당·합계 10,000행(`workbook.ts` 217·301행), 표 합계 5,000행(`contracts.ts` 64·83행), 차트 500행(111행), `analysis` 700,000자(`tool.ts` 514행), checkpoint 1,000,000자(`flow.ts` 158·165행). 합성 측정 기준 전체 결과 `analysis`는 1,311,006자로 마지막 두 한도를 모두 넘는다. “숫자 하나를 올리면 다른 곳에서 실패한다”는 문서 판단이 정확하다.
> - 가장 효과가 큰 단일 변경은 `rowSources` 압축이다. 지금은 행마다 파일 ID·시트명을 반복한다. 범위별 연속 구간으로 인코딩하면 68만 자가 1천 자 미만이 된다. 사용처가 `render.ts`의 `evidenceText`뿐이라 변경 범위가 좁다.
> - checkpoint: `finish()`가 결과 전체를 저장하므로(§0.2-2) 완료 checkpoint에는 plan·sources·결과 요약만 두고, 재출력 때는 fingerprint 확인 후 plan을 다시 실행해 결과를 재생성하는 방식을 권한다. 결정적 실행이라 재현 가능하고, 원본 변경 시 기존 fingerprint 검사로 막힌다. 재출력 경로(`tool.ts` 242~259행)도 같이 바꿔야 한다.
> - 차트 데이터 분리: 차트 전용 결과를 표와 분리하더라도 “모든 입력 ID는 `sourceRows` 또는 `excluded`에 정확히 한 번” 규칙(`contracts.ts` 105~106행)은 유지해야 한다. 차트 시리즈가 입력 행을 1:1로 쓰는 경우 “전 행 사용”을 표시하는 압축 표현을 허용하는 쪽이 검증 규칙을 덜 흔든다.
> - 출력: 차트만 원하는 요청에도 지금은 HTML에 1만 행 표와 행별 “원본 행” 열이 함께 들어간다. PDF는 수백 쪽이 된다. 표 생략·요약 표 옵션을 함께 정해야 한다.
> - 위험: 출처·검증 규칙이 바뀌는 유일한 항목이다. 기존 보고서 재출력 호환과 회귀 테스트(`analysis.test.ts`, `output.test.ts`, `flow.test.ts`)를 가장 넓게 확인해야 한다.

### G. 오류 표시·시간 기록·재개 비용의 구분이 부족함 — P1/P2

`BusinessFlow.retry()`는 내부 검증 오류도 입력 카드로 돌려보낸다. 사용자에게 필요한 기준 질문과 시스템 실패의 차이가 흐려진다. `event()`는 상세 phase를 UI에 보내지만 trace에는 대체로 `tool.started`와 `localOnly`만 저장한다. 모델 클라이언트가 계산한 호출 시간·토큰 사용량도 이 Excel 경로에서는 run별 trace로 충분히 남지 않는다.

재개 때 파일 재읽기와 프로파일 생성도 반복한다. 다만 이번 실행에서 관찰된 초기 약 1.3~1.5초는 긴 모델 대기보다 작으므로 캐시 최적화는 후순위다. fingerprint 확인은 원본 변경을 막는 기능이므로 삭제하면 안 된다.

**개선:** 사용자 결정 필요 / 알려진 제약 / 내부 계약 오류 / 모델·네트워크 실패를 구분한다. 내부 오류에 사용자 답변 수정을 요구하지 않는다. 파일 확인·계획 해석·실행·검증·렌더링의 로컬 시간과 오류 코드를 기록한다. 이후 fingerprint와 파서 버전이 같은 구조 프로파일을 재사용하고, 요청에 따라 달라지는 검색 결과는 별도로 갱신한다.

근거: [flow.ts](../electron/business/flow.ts) 122, 291, 295행 / [tool.ts](../electron/excel/tool.ts) 275, 611행 / [workerClient.ts](../electron/excel/workerClient.ts) / [workbook.ts](../electron/excel/workbook.ts) 12행.

> **타당성 검토 (G)** — 판정: 타당 / 규모 계측 S, 오류 분류 M, 캐시 후순위 / 위험 낮음
>
> - 확인: `retry()`(292~294행)는 모든 오류를 입력 카드로 되돌린다. `event()`(295~299행)는 trace에 `{ localOnly: true }`만 기록하고 phase 문자열은 UI에만 보낸다. 문서 설명이 맞다.
> - 계측 구현: `TraceWriter.record`는 임의 payload를 받으므로 phase·경과 시간·오류 코드를 넣기 쉽다. 모델 호출 정보는 `harnessModel.lastCallFor(signal)`로 이미 얻을 수 있다(ChatWorkflow·Canvas가 같은 방식을 쓴다). 남는 작업은 tool `execute` 입력에 `onTrace` 콜백을 추가하는 것뿐이다. 파일 내용·답변을 넣지 않는 원칙은 payload 스키마로 강제하면 된다.
> - 오류 분류: tool이 지금은 일반 `Error`만 던진다. `ExcelLimitError`·`ExcelContractError` 같은 코드가 있는 오류 클래스를 두고 `retry()`가 코드별 문구를 고르게 하면 된다. worker 경계는 메시지 문자열만 전달하므로(`excel.worker.ts` 18행) 코드도 함께 직렬화해야 한다.
> - 캐시: 재개마다 `deps.session()`으로 새 worker를 띄워(`tool.ts` 612행) 파싱 캐시가 사라진다. 관찰된 1.3~1.5초는 모델 대기보다 훨씬 작으므로 후순위 판단에 동의한다.

## 6. 제안하는 처리 흐름과 역할

```text
파일 읽기·구조 확인
  → 요청을 작은 실행 계획으로 해석
  → 열·범위·단위·지원 기능·예산 검증
  → 필요한 업무 의미만 질문
  → 최신 답변으로 현재 계획 갱신
  → 검증된 차트 실행 코드
  → 결과·출처 검증
  → HTML 생성
```

| 구성요소 | 담당 |
| --- | --- |
| Harness | 요청 소유권, start/resume/cancel, workflow 변경 |
| BusinessFlow | 입력·질문 상태 저장, 파일 접근·fingerprint 확인, 취소, 결과 전달 |
| Excel planner | 자연어를 지원되는 실행 계획으로 해석, 의미가 모호한 조건 질문 |
| Excel validator / worker | 범위·단위·지원 기능 검사, 데이터 추출·계산, 자원 제한 |
| Chart renderer | 승인된 계획의 축·시리즈·출력 형식으로 렌더링 |

다음은 의미 확인이 끝난 뒤 사용할 수 있는 **설명용 계획 예시**이며 확정 API가 아니다. 원본 C열을 그대로 그리는 것으로 확인된 경우를 가정한다.

```json
{
  "kind": "chart",
  "fileId": "file1",
  "sheet": "1006R1-V normal",
  "headerRow": 1,
  "range": { "firstDataRow": 2, "lastDataRow": 10870 },
  "x": { "column": 2, "scale": "linear", "label": "Temperature", "unit": "℃" },
  "series": [
    { "column": 3, "axis": "left", "label": "Weight", "unit": "%" },
    { "column": 4, "axis": "right", "label": "Deriv. Weight", "unit": "%/℃" }
  ],
  "format": "html"
}
```

LLM이 만든 계획도 신뢰 경계에서 검증한다. 선택하지 않은 파일, 존재하지 않는 열, 임의 실행 코드 등을 허용하지 않는다. 새 기본 경로 때문에 기존 QuickJS 격리나 파일 접근 정책을 완화하지 않는다.

첫 배포를 HTML 이중축까지로 한정할 수 있다. 이 경우 PDF/XLSX의 새 기능 지원 여부를 명시적으로 검사하고 기존 기능의 회귀를 막는다. 지원하지 않는 형식으로 조용히 변환하거나 다른 차트로 대체하지 않는다.

### 저장 상태 호환성

- 기존 `answer1~3`와 clarification 이력을 새 현재 상태로 읽는 호환 규칙을 정의한다. 충돌 시 최신 저장 입력을 우선하되, 재사용된 키로 과거 모든 질문을 덮지 않는다. 확정할 수 없는 현재 조건만 다시 확인한다.
- `tool.version`이 바뀌면 현재 BusinessFlow는 기존 대기 작업 재개를 거부한다. 버전 증가만으로 해결하지 말고 호환 읽기 또는 명시적인 새 작업 전환을 결정해야 한다. (검토 추가) 단, `start()`가 이전 완료 run의 checkpoint를 버전 확인 없이 복사하므로 호환 읽기는 어느 쪽을 택해도 필요하다(§0.2-7).
- 조건 변경 시 기존 계산·보고서의 유효성을 판단한다. 시트·범위·계산 의미가 바뀌면 해당 결과를 무효화하고 원본 구조 캐시는 재사용할 수 있다.
- 기존 결과 파일은 덮어쓰지 않고, 원본 파일 변경 감지와 취소·중복 제출 방지를 유지한다.

## 8. 검증 계획과 수용 기준

### 기능 및 회귀 테스트

1. 같은 질문의 답변을 수정하면 최신값만 현재 조건으로 전달된다. 이력은 남는다.
2. 네 번째 이후 질문도 고유하게 연결되며 이전 답변을 덮지 않는다. 입력 카드 필드 수가 무한히 증가하지 않는다.
3. 번호·선택지 클릭과 자유 텍스트 수정 모두 처리한다. 선택지 ID와 질문 ID를 연결하고, 모호한 “2번”은 잘못 적용하지 않는다.
4. 기존 checkpoint를 읽어 재개하고, 조건 변경 후 오래된 보고서를 그대로 반환하지 않는다.
5. `chart` 생략 + 정상 `charts`를 일관되게 처리한다. 잘못된 차트·열·출처·숫자 검증은 유지한다.
6. 알려진 행 제한과 미지원 형식은 코드 생성 전에 처리한다. 불가능한 2,000개 점 선택지를 제안한 뒤 500개 제한을 다시 묻지 않는다.
7. TGA 선택 시트의 B2:D10870 전체 10,869개 행이 정확히 연결된다. 첫 행·마지막 행·중간 지점·미분 피크와 원본을 대조한다.
8. X좌표는 실제 온도 간격을 반영한다. 두 시리즈는 각각 왼쪽·오른쪽 축과 올바른 단위를 사용한다. 측정 순서·결측 구간·반복 온도 처리 정책을 검증한다.
9. 원본 `Weight (%)`와 계산된 `Weight Loss (%)`를 혼동하지 않는다. 99.9라는 원시 값을 9,990%로 표시하지 않는다.
10. 취소, worker 종료, 원본 변경, 계정 전환, 대기 상태에서 앱 재시작, 기존 단일축 차트·PDF·XLSX 출력의 회귀를 확인한다.

단위 테스트에는 합성 데이터와 고정 모델 응답을 사용한다. 제공받은 실험 파일은 별도 로컬 수용 테스트에 사용하고, 저장소 fixture로 추가할지는 별도로 결정한다. 모델 mock 통과를 실제 서비스의 응답 품질·속도 검증으로 간주하지 않는다.

### 검토안에서 조정한 점

- 질문 키는 현재 질문 하나의 고정 `answer` 대신 증가하는 `answerN`을 쓴다. 입력 카드는 기반 필드와 현재 질문만 보이므로 30필드 제한을 넘지 않는다. 구 대기 작업을 읽기 위해 도구 버전 `0.4`를 유지한다.
- HTML과 PDF는 새 이중축 경로를 지원한다. 새 dataset·이중축 XLSX는 명시적으로 거부한다. 기존 XLSX 표·단일축 차트는 유지한다.
- 완료 checkpoint에서 전체 분석을 제거하되, **임의 생성 코드를 재출력할 때 다시 실행하지 않는다.** Date/Math.random 등으로 결과가 바뀔 수 있기 때문이다. 일반 분석은 출력 실패 시 작은 결과 snapshot을 보관하고, 이를 저장할 수 없을 정도로 크면 재실행을 안내한다. 재계산 재출력은 고정된 chart 계획에만 허용한다.
- 파일/요청이 바뀌면 상태를 버리고, revision·답변·형식 변경은 오래된 출력 결과를 무효화한다. 이전 완료 결과 요약은 문맥으로만 전달하고 새 조건의 실행을 대체하지 못한다.
- 파서 전체 캐시의 장기 보관은 추가하지 않았다. 같은 query의 축소 프로파일만 재사용하며, 새 자연어 답변은 검색 결과를 갱신한다.

### 테스트 결과

- Node 24.22.1에서 전체 Vitest **526개 통과, 5개 기존 조건부 테스트 skip** (60개 파일 통과, 3개 파일 skip).
- `npm run typecheck:electron`, `npm run lint`, `npm run build` 통과. 생성물 디렉터리를 lint에서 제외하고 기존 모델 테스트/정규식의 lint 오류 4건도 함께 정리했다.
- `scripts/excel-chart-smoke.ts`: 실제 Electron utility worker와 QuickJS, HTML 생성, Chromium PDF 인쇄를 사용한다. ExcelJS로 별도 읽은 B/C/D의 모든 숫자와 출처 행을 결과와 하나씩 비교하고, 원본 SHA-256 불변과 checkpoint 한도를 검증한다. 개인 실험 파일·출력·모델 응답은 Git에 포함하지 않았다.

### 실제 TGA 측정

선택 시트 `1006R1-V normal`, 10,869개 B/C/D 숫자 행, C열은 사용자 확인 후 원본 Weight(%)를 유지하는 시나리오다. 자동 테스트의 답변은 즉시 제출했으므로 사람이 생각한 대기 시간은 포함하지 않는다. 다음은 동일 Mac에서의 단일 측정이며 성능 보장이나 엄격한 통계 비교가 아니다.

최종 실행은 “Weight Loss(℃)”와 원본 “Weight(%)”의 차이를 한 번 질문하고, “원본 Weight(%)로 표시”라는 자유 텍스트 답변 후 `chart` 계획을 반환했다. 두 시리즈 모두 10,869개 점을 사용했다. 입력 토큰은 호출당 약 51,000에서 **12,087 / 12,405**로 감소했고, 최종 HTML 323,970 bytes / PDF 295,229 bytes / checkpoint 24,828자 / 출처 범위 80자였다.
