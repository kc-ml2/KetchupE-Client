# 일일자금일보 ERP 연동 작업 기록

2026-11-03. `dev` 브랜치를 기존 `origin/dev`의 `1beba43`까지 fast-forward한 뒤 작업했다. 새 커밋이나 푸시는 하지 않았다. 기존 계좌 연결·입출금 보정 폼 개선을 포함한 상태에서 `daily_cash` 업무 버전을 `1.1.0` → `1.2.0`으로 변경했다.

## 구현 결과

첫 입력은 작업일, 전일 일보 XLSX, 주간자금계획 XLSX다. 자금현황 엑셀 업로드 항목과 파일명 기준일 확인을 제거했다. KC 자금현황은 서버의 조회 전용 `erp_cash_status_kc`에서 받아 기존 계좌 모델로 변환한다. 계산과 엑셀 작성은 기존 업무 코드가 수행한다.

조회 → 계좌 연결 → 실제 집행·계획 확인 → 잔액 대사 → 환율 조회 → 최종 확인 → XLSX/PNG 생성 순서다. 실제 거래의 적요는 ERP 계좌 현황에 없으므로 담당자 확인 단계가 계속 필요하다. 잔액 차이를 임의의 거래로 채우지 않는다.

## MCP 확인과 REST 선택 근거

실제 키로 MCP의 initialize, `tools/list`, `tools/call`을 실행했다. 2026-10-14 조회가 성공했고 50계좌를 반환했다. 기존 앱의 Streamable HTTP 클라이언트와 연결 가능하다.

다만 도구의 `outputSchema`가 없고 `structuredContent`도 없다. 실제 응답은 JSON 배열이 담긴 text 블록(32,296자)이며 배열 자체에 `rowCount`와 `truncated`가 없다. 한 번의 응답이 JSON으로 파싱된다는 사실만으로 출력 계약이나 잘림 검증을 보장할 수 없다.

따라서 일보에는 정보팀이 명시한 REST JSON 계약을 사용했다. MCP 연결 실패 후 API를 자동 재시도하는 구조가 아니라, 고정된 REST 경로를 한 번 호출한다.

```text
POST https://caper.kct.co.kr/api/agent-tools/erp_cash_status_kc
Authorization: Bearer <CAPER_API_KEY>
Content-Type: application/json

{"from_dt":"20261014","to_dt":"20261014"}
```

## 조회 기간과 필드 매핑

일보 기준일 D는 작업일 직전 영업일이다. `from_dt=D`, `to_dt=다음 영업일 전날`로 만든다. 예를 들어 2026-10-15 작업은 10월 14일 하루, 11월 2일 월요일 작업은 10월 30일 금요일~11월 1일 일요일, 한글날 다음 월요일인 10월 12일 작업은 10월 8일~11일을 조회한다.

| 기존 업무 값 | ERP 컬럼 / 처리 |
| --- | --- |
| 계좌 식별자 | `FINPRODUCT_CD:통화`. 앞자리 0 유지 |
| 계좌명 / 은행명 | `FINPRODUCT_NM` / `PARTNER_NM` |
| 상품 구분 | `NM_TP_DEPOSIT` |
| 통화 | `EXCH_CD`, 공백·null은 KRW. 지원: KRW/USD/JPY/CNY |
| 원화 기초 / 입금 / 출금 / 기말 장부 | `AM_BASICS` / `ACNT_IAMT_AMT` / `AM_WITHDRAW` / `AM_FINAL` |
| 외화 기초 / 입금 / 출금 / 기말 장부 | 같은 컬럼의 `2` 접미사 값. 원화 환산값으로 대체하지 않음 |
| 실제 마감잔고 | **`BLNC_AMT`**. 기존 KC 엑셀 O열 계좌잔고에 해당 |
| 원화 장부금액 | `AM_FINAL`, 외화 계좌에도 별도 보존 |
| 가입일 / 만기일 | `JOIN_DT` / `END_DT`, YYYYMMDD → YYYY-MM-DD |
| 총 원화 대사 | KRW 계좌의 `BLNC_AMT` 합계. 외화를 혼합 합산하지 않음 |

공휴일 표는 기존 2026~2027년 표를 공유한다. 표 범위 밖이나 아직 종료되지 않은 조회 기간은 차단한다. 주말·휴일 동안 발생한 거래도 ERP 조회에 포함되므로 담당자는 실적 확인에 해당 거래를 반영해야 한다.

## 검증과 데이터 보관

- `success:true`, `truncated:false`, `rowCount === rows.length`를 확인한다. 빈 결과, 필수 컬럼 누락, 중복 계좌/통화, 미지원 통화, 잘못된 날짜·금액을 거부한다.
- 계좌별 기초+입금−출금=기말 장부잔액을 Decimal로 검사한다. 음수 입출금, 가입일·만기일 없는 정기예금은 자동 처리하지 않는다. 은행잔액과 장부잔액은 별개로 유지한다.
- HTTP 오류·인증 거부·연결 실패·잘못된 JSON·응답 도중 중단은 명시적 오류로 반환한다. 60초 타임아웃, 1MiB 응답 상한, 리다이렉트 거부를 적용한다. 자동 반복 호출은 없다.
- 정상 조회 후 필요한 컬럼만 `checkpoint.erpCash`에 보관한다. 추가 질문·최종 확인에서는 같은 스냅샷을 재사용한다. 원본 응답의 `FINPRODUCT_NO` 및 불필요한 컬럼은 저장하지 않는다. 계좌코드·이름·금액은 업무 재개에 필요한 로컬 작업 데이터로 남는다.
- 조회 기간·시각·행 수·응답 해시를 최종 확인 및 감사 데이터에 연결한다. 계좌별 적용 잔고는 기존 최종 확인 화면에서 검토한다. 재조회하려면 새 작업을 시작한다.
- 키는 `.env.caper.local` 또는 실행 환경변수에서 읽는다. 개발 메인 프로세스가 파일을 읽고 worker가 환경변수를 상속한다. 키를 renderer, IPC 입력값, 체크포인트, 결과 파일 또는 Vite define에 넣지 않았다. 빌드 파일 346개를 실제 키와 비교해 포함되지 않았음을 확인했다.

## 제공 샘플로 확인한 결과

입력: `261013_일일자금일보.xlsx`, `261014_자금현황표[KC].xlsx`, `주간자금계획서_1009.xlsx`. 실제 생성 실행에는 전일 일보와 주간계획만 전달했고, KC 엑셀은 ERP 비교용으로만 읽었다.

1. 샘플 일보에는 `261013`과 `261014` 두 시트가 있었다. 원본을 그대로 넣으면 기존 중복 방지가 동작했다. 검증에서는 13일 시트만 담은 메모리 사본을 입력하고 기존 14일 시트를 비교 대상으로 삼았다. 원본 3개 파일의 SHA-256이 작업 전후 같음을 확인했다.
2. REST 응답은 50행, 잘림 없음. 엑셀의 50계좌와 모두 매칭됐고 **50개 은행잔액·가입일·만기일, 원화 은행잔액 합계가 일치**했다. 자동 계좌 연결도 50개 모두 성공했다.
3. 엑셀과 현재 ERP 사이에 **원화 2계좌의 장부 값 차이**가 있었다. 은행잔액과 외화 금액은 일치했다. 과거 파일과 현재 ERP의 장부 값이 다른 이유는 응답만으로 확정하지 않았다. 값을 엑셀에 강제로 맞추지 않고 현재 ERP를 사용했다.
4. 주간계획의 14일 지주현금 계획은 없고 15일 지급계획은 5건이었다. 검증용 실제 거래는 기존 14일 일보에 있는 **법인카드 입금 48,200원 1건**을 근거로 입력했다. ERP 잔액 차이만으로 거래 내용을 추정한 것이 아니다. 테스트에서 최종 확인을 진행했으며 운영 담당자의 승인으로 간주하지 않는다.
5. 하나은행에서 2026-10-14 최종 **1206회차**를 실제 조회했다. USD 1,343원, JPY 1엔당 8.4944원(100엔당 849.44원), CNY 200.63원으로 참고 일보와 일치했다.
6. 계좌별 이월·증감, 지주현금 실적 마감, 총 원화, 예금 만기·가입 원금 대사와 최종 확인 검사 **5개 모두 통과**했다. XLSX를 재열었고, 보존된 13일 시트의 셀 값·수식도 입력 사본과 일치했다. PNG는 2672×5480 픽셀로 생성됐다.
7. 기존 `261014` 시트와 A:P의 숫자가 있는 **609개 위치를 비교**했다. 606개는 일치하고, 아래 3개는 동일한 원천계획 차이에서 발생했다.

| 위치 | 차이 원인 |
| --- | --- |
| `H154` | 인터넷 요금: 주간계획 `세부계획(원화,외화)!L168`은 63,000원, 기존 일보는 55,500원. 생성 결과는 주간계획의 63,000원 |
| `H229` | 15일 지급계획 합계가 7,500원 증가 |
| `H230` | 15일 예상 마감잔액이 7,500원 감소 |

14일 실제 마감잔액·원화 총액에는 이 계획 차이가 영향을 주지 않는다. 15일 요금을 55,500원으로 확정해야 한다면 사용자 계획 편집 표에서 수정하고 다시 최종 확인하면 된다.

실제 금액이 들어간 검증용 파일·응답·스크립트는 Git에서 제외되는 `outputs/caper-validation.local/`에만 두었다. 원본 파일을 수정하지 않았다. 자동 회귀 테스트에는 합성 데이터만 사용한다.

타입 검사와 프로덕션 빌드, 관련 65개 테스트가 통과했다. Electron utility process에서도 빌드된 업무 worker가 새 버전으로 동작하며 중복 시트 방지를 수행하는 것을 확인했다. `node:sqlite`를 사용하는 테스트는 프로젝트 요구사항에 맞는 Node 22.5 이상에서 실행해야 한다. 별도 의존성은 추가하지 않았다.

## 사용과 남은 범위

개발 환경에서 `.env.caper.local`의 `CAPER_API_KEY`를 설정하고 앱을 재시작한다. 새 일일자금일보 작업에서 날짜와 두 종류의 엑셀을 선택하면 ERP를 조회한다. 기존 버전으로 대기 중이던 작업은 새 작업으로 시작해야 한다.

배포본의 사용자별 키 발급·보관 UI와 broker 연동은 이번 범위에 없다. 배포 실행 환경에 안전하게 키를 주입하는 운영 설정이 필요하다. 안내받은 키 만료는 2027-01-27 14:46이다. 실제 앱 화면의 전체 클릭 경로와 설치된 Microsoft Excel에서의 동작·인쇄는 검증하지 않았다. 기존 PNG 렌더러는 Excel의 텍스트 넘침·서식을 완전히 재현하지 않아 샘플의 일부 긴 제목/예금 설명이 잘린다. ERP 연동 외의 이미지 렌더링 코드는 변경하지 않았다.
